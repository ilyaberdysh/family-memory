# Развёртывание Family Memory в Coolify

Одна установка — одно закрытое семейное пространство. Для первого запуска
используйте пустой постоянный том: переносить локальную базу не требуется.
Telegram можно подключить после первого деплоя; до настройки вход будет закрыт.

## 1. Приложение из GitHub

В проекте Coolify создайте приложение из репозитория
`https://github.com/ilyaberdysh/family-memory` и задайте:

| Поле | Значение |
| --- | --- |
| Branch | `main` |
| Build Pack | `Dockerfile` |
| Base Directory | `/` |
| Dockerfile Location | `/Dockerfile` |
| Ports Exposes | `4317` |
| Port Mappings | Оставить пустым |
| Domain | Ваш HTTPS-адрес, например `https://family.example.com` |
| Replicas | `1` |

Команды установки, сборки и запуска задаёт Dockerfile. Отдельный статический
сервис для frontend не нужен. Домен направьте на сервер Coolify и включите HTTPS;
прокси должен обращаться к внутреннему порту `4317`.
[Dockerfile в Coolify](https://next.coolify.io/docs/applications/builds/dockerfile).

В **Advanced** включите **Consistent Container Names**, чтобы обновление сначала
останавливало старый контейнер. Одновременный запуск старого и нового экземпляров
на одной SQLite недопустим для фоновых заданий приложения; короткая пауза при
обновлении ожидаема. Если такого переключателя в вашей версии нет, остановите
приложение перед обновлением. Не подключайте production-том к preview deployments.
[Порядок rolling updates](https://next.coolify.io/docs/applications/deployments/rolling-updates).

## 2. База и файлы

Отдельный ресурс Database в Coolify создавать не нужно. Приложение уже использует
**SQLite**, а аудио, видео и фотографии сохраняет как файлы. PostgreSQL, Redis
и S3 в текущей версии не подключены; переменные `DATABASE_URL` и S3-реквизиты
приложение не использует.

До первого деплоя добавьте в **Persistent Storage** том:

| Поле | Значение |
| --- | --- |
| Type | Volume Mount / Docker Volume |
| Name | `family-memory-data` |
| Source Path | Оставить пустым для named volume |
| Destination Path | `/var/lib/family-space` |

Coolify может дописать UUID ресурса к имени тома — это нормально.
Путь внутри контейнера должен остаться именно `/var/lib/family-space`.
[Постоянные тома Coolify](https://coolify.io/docs/knowledge-base/persistent-storage).

При `DATA_DIR=/var/lib/family-space/data` в этом томе будут:

```text
/var/lib/family-space/
├── data/
│   ├── family.sqlite
│   ├── family.sqlite-wal   # могут присутствовать во время работы SQLite
│   ├── family.sqlite-shm
│   ├── backup-status.json  # итог последней резервной копии
│   └── files/              # оригиналы и подготовленные версии медиа
└── backups/                # автоматические локальные снимки (BACKUP_DIR)
    └── 2026-10-06T03-00-00Z/
```

Схема базы создаётся автоматически. Контейнер работает от `node` с UID/GID
`1000:1000`; каталогу нужны права записи для этого пользователя. Dockerfile
подготавливает родительский каталог. Если используете bind mount вместо нового
тома, заранее назначьте его каталогу на сервере владельца `1000:1000`.
Не меняйте права всех каталогов Coolify и не используйте `chmod 777`.

Не монтируйте том поверх `/app`: там находится код приложения.
Сохраняйте тот же том при redeploy. Удаление тома удалит и базу, и медиа.

Если том забыли подключить, `DATA_DIR` оказывается во временной файловой системе
контейнера и исчезнет при следующем redeploy. Приложение распознаёт это при старте
в контейнере и отказывается запускаться с понятной ошибкой в логе. Подключите том
и повторите деплой. `ALLOW_EPHEMERAL_DATA=1` отключает эту проверку только для
одноразовых тестовых контейнеров; в настоящей установке его не задавайте.

## 3. Переменные окружения

Откройте **Environment Variables** приложения и перенесите значения из
[.env.coolify.example](.env.coolify.example), заменив домен своим.
Для всех перечисленных переменных включите **Runtime Variable** и выключите
**Build Variable**, включая `NODE_ENV`: сборка должна установить и devDependencies.
Сборке frontend секреты не нужны. Не используйте префикс `VITE_`
для ключей и не добавляйте `.env` в GitHub.
[Runtime-переменные Coolify](https://coolify.io/docs/knowledge-base/environment-variables).

Минимум для первого закрытого запуска:

```dotenv
NODE_ENV=production
DEV_AUTH=0
HOST=0.0.0.0
PORT=4317
TRUST_PROXY=1
PUBLIC_ORIGIN=https://family.example.com
DATA_DIR=/var/lib/family-space/data
SPACE_NAME=Семейное пространство
FAMILY_SURNAMES=
```

Замените `PUBLIC_ORIGIN` на свой фактический HTTPS-адрес, без пути и завершающего
`/`. Он должен совпадать с адресом в браузере. `TRUST_PROXY=1` рассчитан на один
прокси Coolify перед приложением. **`DEV_AUTH=0` обязателен в production.**

`FAMILY_SURNAMES` можно заполнить 3–5 фамилиями через запятую. Вместе с
`SPACE_NAME` они будут видны на публичном приглашении. При пустом значении
фамилии появятся по мере ручного заполнения дерева.

Следующие поля пока можно оставить пустыми или не создавать:

| Переменная | Когда нужна |
| --- | --- |
| `TELEGRAM_CLIENT_ID` | Подключение Telegram Login |
| `TELEGRAM_CLIENT_SECRET` | Секрет Telegram Login; только runtime |
| `ADMIN_TELEGRAM_ID` | Личный числовой Telegram ID владельца, задать до первого входа |
| `OPENAI_API_KEY` | Ассистент, расшифровка и извлечение сведений; только runtime |
| `ADMIN_EMAIL` | Только поиск прежнего администратора при переносе; для пустой базы не нужен |

Эксплуатационные параметры уже перечислены в `.env.coolify.example`; значения
по умолчанию подходят для большинства установок:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `BACKUP_DIR` | не задан | Каталог автоматических снимков вне `DATA_DIR`, например `/var/lib/family-space/backups`. Без него автоматических копий нет |
| `BACKUP_INTERVAL_HOURS` | `24` | Как часто делать снимок |
| `BACKUP_KEEP` | `7` | Сколько завершённых снимков хранить |
| `BACKUP_FIRST_DELAY_MINUTES` | `10` | Пауза после запуска перед первой проверкой, нужна ли копия |
| `MIN_FREE_DISK_MB` | `1024` | Ниже этого запаса свободного места загрузки отклоняются, администратор видит предупреждение |
| `SHUTDOWN_TIMEOUT_MS` | `50000` | Сколько ждать завершения текущих запросов при остановке |
| `REQUEST_TIMEOUT_SECONDS` | `3600` | Предельное время одного запроса, чтобы медленная загрузка с телефона не обрывалась |
| `MEDIA_PREVIEW_CONCURRENCY` | `1` | Сколько версий для браузера готовится одновременно |

Без Telegram-параметров сервер запускается, но вход недоступен. Без OpenAI-ключа
ручное наполнение и архив работают после входа, AI-обработка недоступна.
Дополнительные лимиты и модели перечислены в [.env.example](.env.example)
и [README.md](README.md#ассистент-и-данные).

## 4. Первый деплой

Нажмите **Deploy**. Health check в Dockerfile обращается к
`GET /api/health` на порту `4317`; если задаёте проверку в Coolify вручную,
используйте тот же путь и ожидайте HTTP `200`. Ответ `503` означает, что база
недоступна для чтения. Поле `diskLow` в ответе сообщает о нехватке места, но
само по себе не делает контейнер нездоровым.

Проверьте HTTPS-страницу входа. Без Telegram она должна сообщать, что вход пока
недоступен. Запрос `/api/state` без сессии должен возвращать `401`, а production
не должен показывать кнопку локального просмотра.

В терминале контейнера можно проверить хранилище без вывода секретов:

```sh
node -e "const fs=require('node:fs');const p=process.env.DATA_DIR;fs.accessSync(p,fs.constants.W_OK);console.log('Data directory is writable');console.log('SQLite exists:',fs.existsSync(p+'/family.sqlite'))"
```

До подключения пользователей проверьте свободные память и диск. Оригиналы медиа
и их браузерные версии занимают место в томе; размер сервера выбирайте по объёму
загрузок. Состояние резервных копий и свободного места администратор видит
в интерфейсе приложения. Перед приглашением семьи настройте копию за пределами
сервера (раздел 6) и лимиты прокси для больших загрузок (раздел 7).

## 5. Подключение Telegram

Этот шаг можно выполнить позже без пересоздания приложения или тома.

1. В мини-приложении **BotFather → ваш бот → Login Widget** добавьте Allowed URLs:
   `https://family.example.com` и
   `https://family.example.com/api/auth/telegram/callback`, заменив домен на свой.
2. Сохраните оттуда **Client ID** и **Client Secret** в `TELEGRAM_CLIENT_ID`
   и `TELEGRAM_CLIENT_SECRET`. Это отдельные реквизиты Login, не bot token.
   Алгоритм подписи оставьте **RS256**.
3. Задайте `ADMIN_TELEGRAM_ID`: числовой ID **личного Telegram-аккаунта владельца**,
   не ID бота. Сохраните настройки и выполните redeploy.
4. В пустую базу первым должен войти именно владелец с этим ID. До этого
   не распространяйте ссылку регистрации: автоматический первый администратор
   создаётся только для явно указанного ID и пустой таблицы пользователей.

Приложение использует серверный OIDC Authorization Code flow с PKCE и проверкой
подписанного ID-токена. [Официальная инструкция Telegram Login](https://core.telegram.org/bots/telegram-login).

При переносе существующей базы `ADMIN_EMAIL` может выбрать прежнего администратора
для привязки к `ADMIN_TELEGRAM_ID` с сохранением ID и авторства. Задайте параметры
до его первого Telegram-входа; отдельные уже созданные аккаунты автоматически
не объединяются. Для новой пустой установки этот миграционный шаг не нужен.

После входа владельца проверьте с отдельным аккаунтом: заявка → ожидание →
одобрение → выбор «Это я» или пропуск → доступ к дереву. Для человека без Telegram
администратор может выдать одноразовую гостевую ссылку. Затем проверьте загрузку,
запись и воспроизведение с телефона, а также сохранность данных после redeploy.

## 6. Резервные копии и восстановление

Постоянный том защищает от замены контейнера, но не от потери сервера. Защита
строится из трёх частей: автоматические снимки на сервере, зашифрованная копия
за его пределами и регулярная проверка, что из копии действительно можно
восстановиться.

### 6.1. Автоматические локальные снимки

Если задан `BACKUP_DIR` (в `.env.coolify.example` и `compose.yaml` это
`/var/lib/family-space/backups`), приложение само делает снимок раз в
`BACKUP_INTERVAL_HOURS` часов. Снимок содержит согласованную копию SQLite,
все упомянутые в базе оригиналы и версии для браузера, а также `manifest.json`
с размерами и SHA-256 каждого файла. Каталоги называются по времени UTC,
например `2026-10-06T03-00-00Z`; снимок завершён, только если в нём есть
`manifest.json`.

- Неизменившиеся файлы не копируются заново, а связываются жёсткой ссылкой
  с предыдущим снимком. Каждый снимок полон сам по себе, а дополнительное место
  занимают только новые файлы и база.
- Хранятся `BACKUP_KEEP` последних завершённых снимков. Удаляются только
  каталоги с именем такого формата и манифестом этого приложения; прерванные
  снимки убираются через сутки. Остальное содержимое `BACKUP_DIR` не трогается.
- После запуска приложение ждёт `BACKUP_FIRST_DELAY_MINUTES` минут и делает
  снимок, если последний удачный старше интервала. Два снимка одновременно
  не выполняются; при остановке приложения незавершённый снимок удаляется.
- Итог последней попытки записывается в `DATA_DIR/backup-status.json` и виден
  администратору в интерфейсе, включая предупреждение, если удачной копии давно
  не было.

Локальные снимки защищают от ошибочного удаления, неудачного обновления или
восстановления и от повреждения отдельных файлов. Они **не** защищают от отказа
диска, удаления тома, потери сервера или доступа к хостингу: снимки лежат на том же
томе. Файл, связанный жёсткими ссылками, физически хранится в одном экземпляре,
поэтому его повреждение на диске затронет все снимки сразу. Нужна ещё копия
вне сервера (6.2).

**Копия с проблемами.** Если упомянутый в базе файл отсутствует, неполон или
не совпадает с записанной при загрузке контрольной суммой, копия всё равно
создаётся: в неё попадает всё, что удалось прочитать, а проблемы перечисляются
в поле `problems` манифеста. Статус для администратора становится «с проблемами».
Если в предыдущем снимке есть целая версия такого файла, она переносится в новый
снимок (`"recovered": true`), поэтому ротация не удаляет последнюю целую копию.
Проблемы версий для браузера помечены `"preview": true`: их можно подготовить
заново из оригинала. Найдите причину проверкой (6.3) до того, как старые снимки
уйдут из ротации.

Ручной снимок делается тем же скриптом, например в терминале контейнера:

```sh
node scripts/backup.mjs --out /var/lib/family-space/backups/manual-before-upgrade \
  --link-dest /var/lib/family-space/backups/2026-10-06T03-00-00Z
```

`--out` — новый каталог вне `DATA_DIR`; `--link-dest` необязателен и указывает
на предыдущий завершённый снимок. Код выхода `0` — копия чистая, `2` — копия
создана, но с проблемами (они перечислены в выводе), `1` — копия не создана.
Ручные снимки тоже обновляют `backup-status.json`, но в ротацию не входят:
удаляйте их сами.

### 6.2. Копия за пределами сервера

Пример ниже использует [restic](https://restic.readthedocs.io/): копии
шифруются на сервере, хранятся с дедупликацией и проверяются. Хранилище
выберите у другого провайдера или на другом сервере: SFTP, S3-совместимое
хранилище, Backblaze B2. Скрипт запускается на сервере с Docker от root, читает
последний завершённый снимок прямо из Docker-тома и сообщает о результате
во внешний сервис мониторинга.

Один раз на сервере:

```sh
docker volume ls | grep family-memory-data         # точное имя тома в Coolify
install -d -m 700 /root/.config/family-restic
openssl rand -base64 32 > /root/.config/family-restic/password
chmod 600 /root/.config/family-restic/password
export RESTIC_REPOSITORY='sftp:backup@backup-host.example:/srv/restic/family'
export RESTIC_PASSWORD_FILE=/root/.config/family-restic/password
restic init
```

Пароль хранилища должен быть отдельным, а не одним из паролей сервера.
**Сохраните его вне сервера**, например в менеджере паролей владельца: без него
копию невозможно расшифровать, и при потере сервера она бесполезна.

`/usr/local/sbin/family-offsite-backup` (права `700`):

```sh
#!/bin/sh
set -eu
export RESTIC_REPOSITORY='sftp:backup@backup-host.example:/srv/restic/family'
export RESTIC_PASSWORD_FILE=/root/.config/family-restic/password
VOLUME_NAME='имя-тома-из-docker-volume-ls'
HEARTBEAT='https://hc-ping.com/ваш-uuid'
MOUNT=/mnt/family-latest

ok=0
finish() {
  umount "$MOUNT" 2>/dev/null || true
  if [ "$ok" = 1 ]; then curl -fsS -m 10 --retry 3 "$HEARTBEAT" >/dev/null || true
  else curl -fsS -m 10 --retry 3 "$HEARTBEAT/fail" >/dev/null || true; fi
}
trap finish EXIT

volume=$(docker volume inspect --format '{{ .Mountpoint }}' "$VOLUME_NAME")
latest=
for dir in $(ls -1d "$volume"/backups/20*Z* 2>/dev/null | sort -r); do
  if [ -f "$dir/manifest.json" ]; then latest=$dir; break; fi
done
[ -n "$latest" ] || { echo 'Нет завершённого снимка' >&2; exit 1; }

# Постоянный путь позволяет restic не перечитывать файлы, уже сохранённые раньше.
mkdir -p "$MOUNT"
mount --bind "$latest" "$MOUNT"
restic backup --tag family --ignore-ctime "$MOUNT"
umount "$MOUNT"
restic forget --tag family --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --prune
ok=1
```

Запуск раз в сутки через systemd:

```ini
# /etc/systemd/system/family-offsite-backup.service
[Unit]
Description=Family Memory off-site backup
After=docker.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/family-offsite-backup
```

```ini
# /etc/systemd/system/family-offsite-backup.timer
[Unit]
Description=Daily Family Memory off-site backup

[Timer]
OnCalendar=*-*-* 04:30
RandomizedDelaySec=30m
Persistent=true

[Install]
WantedBy=timers.target
```

```sh
systemctl daemon-reload
systemctl enable --now family-offsite-backup.timer
systemctl start family-offsite-backup.service   # первый запуск вручную
```

Вместо systemd подойдёт cron: `30 4 * * * /usr/local/sbin/family-offsite-backup`.

**Сигнал «копия не пришла».** Создайте проверку в
[healthchecks.io](https://healthchecks.io) или аналогичном сервисе с периодом
1 день и запасом в несколько часов и укажите её адрес в `HEARTBEAT`. Сервис
сообщит, если скрипт упал или перестал запускаться, — например, после
переустановки сервера. Раз в месяц проверяйте само хранилище:
`restic check --read-data-subset=10%`.

### 6.3. Проверка данных и копий

`scripts/verify.mjs` только читает данные и ничего не меняет. В терминале
контейнера или через `docker exec CONTAINER_NAME`:

```sh
node scripts/verify.mjs                     # рабочий DATA_DIR из окружения
node scripts/verify.mjs --backup /var/lib/family-space/backups/2026-10-06T03-00-00Z
```

Для рабочих данных скрипт проверяет целостность SQLite, наличие, тип и размер
каждого упомянутого файла, а для файлов с записанной контрольной суммой — и
содержимое. Старые записи без контрольной суммы проверяются только по размеру;
их число выводится отдельно. Файлы в `files/` без записи в базе показываются
списком, но на код выхода не влияют и не удаляются. Для копии проверяются
манифест, размер и SHA-256 каждого файла и целостность базы, без восстановления.
`--quick` пропускает чтение содержимого. Коды выхода: `0` — проблем нет,
`2` — найдены проблемы, `1` — проверку не удалось выполнить.

**Учебное восстановление.** Раз в квартал восстановите последнюю внешнюю копию
на отдельной машине или во временном каталоге и проверьте её:

```sh
restic restore latest --tag family --target /srv/family-drill
chown -R 1000:1000 /srv/family-drill
docker run --rm --user 1000:1000 -v /srv/family-drill/mnt/family-latest:/restore-src:ro \
  IMAGE node scripts/verify.mjs --backup /restore-src
```

Затем выполните восстановление по 6.4 в новый каталог, запустите
`node scripts/verify.mjs --data-dir` для результата и удалите учебную копию.
`IMAGE` — образ приложения: `docker inspect --format '{{.Config.Image}}' CONTAINER_NAME`.

### 6.4. Восстановление

1. Остановите приложение в Coolify.
2. Подготовьте копию. Локальный снимок уже лежит в томе
   (`/var/lib/family-space/backups/...`). Внешнюю копию извлеките на сервер:
   `restic restore latest --tag family --target /srv/family-restore`; нужный
   каталог — `/srv/family-restore/mnt/family-latest`. Файлы, извлечённые restic
   или скопированные через `docker cp`, принадлежат root, а копии создаются
   с правами `0700/0600`, поэтому передайте их пользователю контейнера:
   `chown -R 1000:1000 /srv/family-restore`.
3. Восстановите в **новый** каталог тома временным контейнером того же образа
   от имени UID 1000, чтобы у результата сразу были правильные владелец и права:

   ```sh
   docker run --rm --user 1000:1000 \
     -v VOLUME_NAME:/var/lib/family-space \
     -v /srv/family-restore/mnt/family-latest:/restore-src:ro \
     IMAGE node scripts/restore.mjs --from /restore-src \
       --to /var/lib/family-space/restored-2026-10-06 --app-stopped
   ```

   Для локального снимка второй `-v` не нужен:
   `--from /var/lib/family-space/backups/2026-10-06T03-00-00Z`.
4. Задайте в Coolify `DATA_DIR=/var/lib/family-space/restored-2026-10-06`
   и запустите приложение.
5. Проверьте дерево и воспроизведение материалов, выполните
   `node scripts/verify.mjs`. Прежний каталог удаляйте только после проверки.

Восстановление сначала сверяет контрольные суммы, целостность SQLite и
соответствие файлов базе и только потом создаёт каталог; существующие каталоги
не перезаписываются. Копию с проблемами (6.1) скрипт по умолчанию не
восстанавливает. С флагом `--allow-problems` он восстанавливает всё, что в копии
есть, и перечисляет недостающие или повреждённые файлы; их целые версии ищите
в более ранних снимках или во внешней копии. Файлы с пометкой `recovered`
восстановлению не мешают: копия содержит их целые версии.

Восстановление очищает сессии и незавершённые входы, отзывает старые гостевые
ссылки и не перезапускает AI-задания. Пользователям понадобится войти снова.
В новом `DATA_DIR` ещё нет `backup-status.json`, поэтому до первого снимка
администратор увидит, что копий нет. Подробности формата и локальные примеры —
в [README.md](README.md#восстановление).

## 7. Прокси и большие загрузки

Видео и записи с телефона загружаются долго. Приложение само допускает запрос
до `REQUEST_TIMEOUT_SECONDS` (по умолчанию час), но прокси перед ним обычно
обрывает его раньше.

**Traefik в Coolify.** В Traefik v3 `respondingTimeouts.readTimeout` по умолчанию
равен 60 секундам: загрузка, которая идёт дольше минуты, обрывается. Откройте
**Servers → ваш сервер → Proxy → Configuration** и добавьте в список `command`
для обеих точек входа:

```yaml
- '--entrypoints.http.transport.respondingTimeouts.readTimeout=3600s'
- '--entrypoints.https.transport.respondingTimeouts.readTimeout=3600s'
```

Имена `http` и `https` должны совпадать с уже указанными там
`--entrypoints.<имя>.address`. Значение `0` снимает ограничение полностью.
Сохраните и перезапустите прокси: на несколько секунд это прервёт все
приложения на сервере.
[Настройки таймаутов Traefik](https://doc.traefik.io/traefik/routing/entrypoints/#respondingtimeouts).

**nginx.** Если перед приложением стоит nginx:

```nginx
client_max_body_size 300m;      # не меньше MAX_UPLOAD_MB
proxy_request_buffering off;    # передавать тело сразу, без промежуточного файла
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
client_body_timeout 300s;       # пауза между пакетами, а не общее время
```

**Cloudflare.** В режиме проксирования (оранжевое облако) Cloudflare на тарифах
Free и Pro отклоняет тела запросов больше 100 МБ, а это меньше `MAX_UPLOAD_MB`
по умолчанию. Для адреса приложения включите режим DNS only (серое облако) или
уменьшите `MAX_UPLOAD_MB` до 100.

**Остановка контейнера.** При остановке приложение до `SHUTDOWN_TIMEOUT_MS`
(50 с) дожидается текущих запросов и прерывает идущий снимок. В `compose.yaml`
для этого задано `stop_grace_period: 75s`. В Coolify стандартное ожидание
остановки короче (около 30 с): если ваша версия позволяет задать время остановки
контейнера, установите не меньше 75 с. Если такой настройки нет, уменьшите
`SHUTDOWN_TIMEOUT_MS`, например до `25000`, чтобы приложение успевало завершиться
до принудительной остановки.
